# i18n — Internationalisation Veridian Analytics

## Stratégie actuelle : monolangue français

Veridian Analytics est livré **uniquement en français** pour ses clients
(sites web Robert / Veridian). Aucun toggle de langue n'est exposé dans l'UI.

## Approche d'implémentation : in-place

Pas de système i18n (react-i18next / next-intl / formatjs) configuré. Les
chaînes affichées à l'utilisateur sont **directement écrites en français
dans le code des composants React**, plutôt que via des clés de traduction.

### Pourquoi ce choix

1. **Volume gérable** : l'app analytics tient sur ~30k LOC et ~62 fichiers
   avec strings UI. La maintenance reste tractable sans système i18n.
2. **Latence de chargement** : un système i18n charge des fichiers JSON
   additionnels, ralentit le bundle initial. In-place = pas d'overhead.
3. **Mono-client français** : Robert vend Veridian aux PME françaises.
   Pas de demande commerciale pour l'anglais.
4. **Robustesse** : pas de risque d'oubli de traduction qui afficherait
   une clé brute (`{t('common.save')}` au lieu de "Enregistrer").

## Locale AntDesign + Day.js

Configuré dans `console/src/main.tsx` :

- `ConfigProvider locale={frFR}` pour AntDesign (DatePicker, Pagination,
  Empty, Confirm dialogs, etc. en français natif)
- `dayjs.locale('fr')` pour formatage des dates relatives ("il y a 3 jours")
- `toLocaleDateString('fr-FR')` pour les dates utilisateur

## HTML lang

`console/index.html` → `<html lang="fr">` pour accessibilité, SEO,
correcteurs orthographiques navigateur.

## Quand re-considérer i18n

Si dans le futur :

- Un client demande l'anglais
- Veridian s'ouvre à l'international (peu probable, marché FR mono-client)
- Un partenaire revend Veridian dans d'autres pays

Alors migrer vers **react-i18next** :

1. `pnpm add react-i18next i18next`
2. Extraire toutes les chaînes via un script vers `locales/fr.json`
3. Wrapper l'App avec `<I18nextProvider>`
4. Remplacer toutes les chaînes par `t('clé')`
5. Ajouter `locales/en.json`, etc.

Volume estimé pour migration : ~1 journée de travail (script d'extraction
+ remplacement + tests).

## Strings techniques

Les éléments suivants restent en **anglais** par convention :

- Variables, fonctions, classes CSS, IDs HTML
- Noms de produits/SaaS (Veridian, Stripe, Anthropic, Cloudflare, OVH)
- Sigles techniques (URL, API, HMAC, SDK, GSC, SMTP, UTM)
- TimeScore (terme produit Veridian)
- Search Console, Lighthouse (noms propres Google)

## Strings traduites

Tout ce qui est affiché à un utilisateur final est en français, vouvoiement
par défaut ("Connectez-vous", "Vos paramètres"). Voir la convention dans
les commits `feat: french-i18n`.

## Convention vouvoiement

- ✅ "Connectez-vous à votre dashboard"
- ✅ "Vos paramètres ont été enregistrés"
- ❌ "Connecte-toi" (tutoiement réservé au wizard d'onboarding qui dialogue
  avec le client de manière proche — cf. `welcome.tsx`)

## Format des nombres et dates

- Dates : `dayjs.locale('fr')` + `format('D MMM YYYY')` → "23 mai 2026"
- Heures : `HH:mm` (24h) — pas d'AM/PM
- Nombres : séparateur français possible avec `toLocaleString('fr-FR')`
  (espace milliers, virgule décimale)
- Devises : symbole respecté (€, $, £)
